# ADR-0009: Client-generated ids and idempotent POST requests

- Status: Accepted
- Date: 2026-11-15
- Story: CN-01

## Context

Rule 11 of the project requires every POST that creates a record to accept a uuid v7 generated by the client and to be idempotent: resending the same request returns the existing record, while reusing an id with different content, or an id that is not visible to the caller, returns 409. The rule does not say how "the same content" is decided, nor how it applies to endpoints that create sessions.

## Decision

**Id validation.** The request carries `id`. The API rejects with 422, before any database access, an id that is not version 7 with the RFC 9562 variant, or whose embedded timestamp differs from `Clock.now()` by more than one day.

**Idempotent create flow.** It is implemented once as a FastAPI dependency plus a use-case helper (CN-05), and runs in the request transaction, after the organization lock when the operation takes it:

1. Look up the id in the target table. RLS hides rows of other organizations.
2. **Not found:** insert. If the insert fails with a unique violation on the primary key, the id exists in another organization, and the API returns 409 `id_conflict`.
3. **Found:** compare the request with the stored record. If they are equal, return the existing record with 200 and do nothing else (no audit event, no job). If they differ, return 409 `id_conflict`.

A successful creation returns 201.

**What "the same content" means.** Each create use case defines a comparison between its validated command and the stored record. The comparison covers:

- every field the client sent, compared after the same normalization the use case applies before storing;
- the acting user (`created_by` or `decided_by`), because the same decision made by another person is a different decision;
- for file uploads, the SHA-256 of the content, plus the kind, account and profile, instead of the raw bytes.

Fields the server derives (`created_at`, computed amounts, status) are excluded. Comparing against the stored record avoids a separate table of request hashes, and the record is the single source of truth.

**Scope.**

- Covered: every POST that creates a business record, including those whose record is a job (`run_engine`, `ai_suggest`, `export_period` and similar). Replaying such a request returns the same job, so a retried click never enqueues twice.
- Not covered: endpoints that create sessions (login, choosing an organization, demo role switch). Session ids and tokens must be server-generated secrets; letting a client choose them would enable session fixation. Accepting an invitation creates a membership keyed by organization and user, which is idempotent by that key. Logout and other actions that only revoke are naturally idempotent.
- Batch actions (confirm or approve in batch, CN-15) carry one client id per decision they create.

**Frontend.** The id is generated when the user starts an action (opens a form or presses a button) and is reused on every retry of that action. Starting a new action generates a new id (CN-06).

**Tests (CN-05, then per endpoint).** For each create endpoint: resending the same request returns 200 and the same record; the same id with different content returns 409; an id existing in another organization returns 409; a non-v7 id and an id with a skewed timestamp return 422.

## Consequences

- Network retries and double clicks are safe everywhere, without an idempotency-key table or column.
- Each create use case must implement and test its comparison. The helper requires one, so it cannot be forgotten.
- The 409 for an id of another organization reveals that the id exists somewhere. uuid v7 ids carry dozens of random bits per millisecond, so enumerating them over HTTP is impractical, and nothing else about the record is revealed.

## Alternatives considered

- **An `Idempotency-Key` header with a stored request hash and response.** Rejected: an extra table with RLS and grants, and the stored response duplicates the record.
- **A `request_hash` column on every creatable table.** Rejected: it ties the schema to the HTTP layer and breaks when a field is renamed.
- **Server-generated ids with deduplication heuristics.** Rejected: heuristics cannot tell a retry from a genuine second record.
